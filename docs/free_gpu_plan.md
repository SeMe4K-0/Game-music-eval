# Бесплатные GPU: что из работы туда реально уносится

Оценка сделана 2026-09-04 против фактических требований пайплайна, а не по
рекламным описаниям площадок. Проверенные факты помечены источником.

## 1. Что вообще требует GPU

| Стадия | GPU | Стоимость | Куда можно унести |
|---|---|---|---|
| `corpus_prep` — окна референса | нет | CPU, минуты | MacBook |
| `run_experiment` — генерация | **да** | ~120 GPU-часов, 9 600 треков | любая площадка |
| `compute_track_metrics` — группы 3–4 | нет | **1.8 CPU-часа на весь план** (замерено) | MacBook или те же ядра рядом с GPU |
| CLAP score (группа 2) | желательно | минуты | там же, где генерация |
| `compute_distributional` — эмбеддинги для FAD/KAD | да | ~1 GPU-час | там же, где генерация |
| FAD/KAD по эмбеддингам | нет | numpy, минуты | MacBook |
| `summarize` | нет | секунды | MacBook |

Вывод: узкое место ровно одно — генерация. DSP-метрики стоят 0.7 с CPU на трек
и считаются на простаивающих ядрах, пока GPU занят следующим треком.

## 2. Два ограничения, которые решают всё

### 2.1 Аудио нельзя возить между площадками

Полный план в PCM_24: musicgen 14.5 ГБ, ace_step 43.5, riffusion 16.6,
audioldm2 6.0, stable_audio 4.9 — **около 85 ГБ**. Kaggle сохраняет 20 ГБ
вывода, бесплатный Google Drive — 15 ГБ.

Решение реализовано в `src/remote_worker.py`: генерация, метрики и эмбеддинги
считаются в одной сессии, аудио удаляется сразу после метрик. Наружу уходят
метрики (десятки МБ) и CLAP-эмбеддинги (около 1 ГБ float32 на весь план).
Архивно сохраняется `--keep-audio sample` — по паре треков на клетку, чтобы
можно было пересчитать метрики без полной перегенерации. Полная
перегенерация как способ восстановления не годится: **на другом железе тот же
сид не даёт то же аудио** (другие ядра CUDA, другой порядок редукций).

### 2.2 bfloat16 есть не везде

T4 (Turing, sm_75), P100 (Pascal, sm_60) и M4000 (Maxwell) не имеют
аппаратного bf16 — он появился в Ampere (sm_80). ACE-Step по умолчанию просит
bf16.

Молчаливый переход на fp16 на T4 означал бы, что модель на разных площадках
считается в разной точности, то есть точность становится скрытым фактором,
спутанным с моделью. Поэтому dtype прибит в `configs/models.yaml`, а
`src/env_info.py` падает с внятной ошибкой вместо подмены.

**Следствие: ACE-Step на Kaggle и Colab недоступен.** Остальные четыре модели
(float16) идут везде. Если ACE-Step нужен на T4 — менять dtype на float16
глобально и перегенерировать все клетки этой модели, а не только новые.

## 3. Площадки

| Площадка | GPU | VRAM | bf16 | Сессия | Квота | Персистентность | Годность |
|---|---|---|---|---|---|---|---|
| **Kaggle** | T4 ×2 или P100 | 15/16 ГБ | нет | 12 ч | 30 ч/нед, сброс в субботу | 20 ГБ `/kaggle/working` + 58 ГБ временных | **основная рабочая лошадь** |
| **Lightning AI** | T4 … L4/L40S/A100/H200 | до 80+ ГБ | на L4 и выше — да | студия перезапускается каждые 4 ч | 80 GPU-ч/мес (15 кредитов) | **100 ГБ постоянных** | **единственная для ACE-Step** |
| **Colab (free)** | T4 | 15 ГБ | нет | 12 ч, простой 90 мин | не публикуется, ~12–30 ч/нед, GPU не гарантирован | Google Drive 15 ГБ | запасная к Kaggle |
| SageMaker Studio Lab | T4 | 16 ГБ | нет | 4 ч, не более 4 ч/сутки | — | 15 ГБ | только фаза 0 |
| Paperspace Gradient | M4000 | 8 ГБ | нет | 6 ч | перезапуски | — | **не годится**: Maxwell без быстрого fp16, 8 ГБ мало |
| HF ZeroGPU / Spaces | H200 | 70–141 ГБ | да | **60 с на вызов, 5 мин/сутки** | — | — | **не годится для пакетной генерации** |
| Groq / Together / Cerebras | — | — | — | — | — | — | **не годится**: это API к чужим LLM, своих весов не запустить |

Kaggle даёт вариант **T4 ×2** — два процесса на разные карты в одной сессии
удваивают выработку за тот же час квоты (`CUDA_VISIBLE_DEVICES=0` и `=1`).

## 4. Что делать прямо сейчас, пока 3060 занята

Порядок по убыванию отдачи на потраченный GPU-час.

### Шаг 1. Фаза 0 — проверка API и VRAM (30–60 минут GPU, Kaggle)

Самое ценное, что можно сделать на чужой карте. Код писался по исходникам
библиотек, но между написанием и прогоном версии меняются; сейчас неизвестно,
работает ли хоть один из пяти бэкендов. Скрипт грузит модель, генерирует один
короткий и один самый длинный трек, замеряет пик VRAM и время, проверяет, что
выход не вырожден, и переживает падение любой модели без потери остальных.

```bash
bash scripts/remote_setup.sh musicgen_small audioldm2_music stable_audio_open_1_0
python -m scripts.phase0_check --isolate
```

Отдельной сессией (у riffusion-hobby старые пины, ставить рядом с новыми
diffusers не стоит):

```bash
bash scripts/remote_setup.sh riffusion_v1
python -m scripts.phase0_check --models riffusion_v1
```

Это сразу отвечает на вопросы, без которых основной прогон планировать нельзя:
какие API отвалились, влезает ли AudioLDM2 на 120 с в 15 ГБ, сколько на самом
деле секунд стоит трек у каждой модели.

### Шаг 2. Пилот на малом N (2–3 часа GPU)

Весь план в миниатюре: все модели и длительности, но два трека на промпт и
один набор. Проверяет пайплайн целиком и даёт первый черновик таблиц.

```bash
python -m src.remote_worker --max-tracks 2 --sets 0 \
    --keep-audio sample --sample-per-cell 1 \
    --out-dir /kaggle/working/results --pack /kaggle/working/pilot.tar.gz
```

### Шаг 3. Массовая генерация четырёх fp16-моделей

Клетка (модель × длительность) целиком считается на одной площадке — иначе
железо окажется спутанным с моделью внутри одного сравнения. Раздача:

```bash
# Kaggle, сессия 1
python -m src.remote_worker --models riffusion_v1 --keep-audio none \
    --out-dir /kaggle/working/results --pack /kaggle/working/riffusion.tar.gz
# Kaggle, сессия 2 (или вторая карта T4)
python -m src.remote_worker --models audioldm2_music --keep-audio none ...
```

Либо автоматическая раздача по площадкам: `--shard 0/3`, `--shard 1/3`,
`--shard 2/3` — хэш по клетке, покрытие ровно один раз (проверено тестом).

Бюджет: riffusion ~34 ч, audioldm2 ~50 ч, musicgen ~23 ч, sao ~9 ч. Kaggle
даёт 30 ч/нед, Lightning — 80 ч/мес. То есть четыре модели закрываются
примерно за 3–4 недели бесплатных квот, либо за несколько суток на 3060, когда
она освободится.

### Шаг 4. ACE-Step — только Ampere и новее

Lightning AI (L4/A100) в пределах 80 ч/мес, либо 3060 после освобождения.
Бюджет ACE-Step ~5 ч — модель быстрая, это самая дешёвая из пяти.

## 5. Что остаётся на MacBook

Подготовка референса, калибровка порогов вырожденности, FAD/KAD по присланным
эмбеддингам, сводные таблицы, решающее правило, текст статьи. Ничего из этого
GPU не требует, и всё это можно делать параллельно с чужими прогонами.

## 6. Чего делать не нужно

- **HF ZeroGPU** для генерации: 5 минут в сутки против 120 GPU-часов.
- **Paperspace M4000**: Maxwell, 8 ГБ — не тянет ни ACE-Step, ни комфортно SAO.
- **Бесплатные inference API** (Groq, Together, Fireworks): они дают доступ к
  чужим развёрнутым моделям, а нам нужно запускать конкретные веса со своими
  сидами и своими параметрами. Не применимо в принципе.
- **Кредиты Google Cloud / AWS / Azure**: требуют карту и сгорают по сроку;
  для 120 GPU-часов проще дождаться 3060.
